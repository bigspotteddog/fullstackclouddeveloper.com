An operating model for AI-assisted engineering

The Agent Drives,
I Navigate

How I run a team of AI developers with XP discipline

Most teams have figured out how to get AI agents to write code. The harder problem is trusting what they write. A better prompt or spec only covers the start. My answer: stay in the loop the whole way, and make the agents verify intended behavior in a running system before anyone reviews it. I no longer write most of the code, but I’m still hands-on: architecture, requirements, review, technical decisions, accountability for delivery.

The guiding principle

Autonomous execution,
not autonomous approval.

Agents plan, implement, test and integrate. Humans decide what ships.

This is the one idea to remember. I work with AI agents as an engineering team, not as a code-generation feature. The approach draws on years of practicing Extreme Programming across multiple teams. It’s an adaptation of XP, not a claim that every XP practice is enforced automatically.

Where it came from

Five stages since early 2025

01

A board the agents walked

Jira, aider and n8n. Agents moved tickets; I reviewed markdown plans, not running code.

02

Real work, on my machine

Three to five agents on a real codebase, verified end to end against the whole system locally.

03

Agents check their work

My own agents; one in the browser, validating against the running application.

04

Parallel and test-first

Agents in separate browser tabs, each on its own branch, building full-stack apps.

05

The fleet

The same process on separate compute instances, each with a complete environment.

Constant at every stage: human direction → agent execution → human review → merge.

This is a personal way of working, used at more than one company and on my own projects. In stage one I was proving the process, not the work: “testing” meant judging whether a plan would work. As agents improved, the same loop could carry real work, and testing moved from me judging a plan on paper to agents validating working software. I carried forward the process, not the architecture. The fleet’s infrastructure wasn’t planned upfront; it grew out of retrospectives.

When something fails, the manager reports it and waits for my direction.

I work at the initiative level: epics, not individual tickets. Work starts from existing tickets or from a discussion that produces new ones. The terminal agent decides whether an initiative needs one developer, several in parallel, or a dedicated manager; a manager keeps monitoring even when my laptop sleeps. Story: a manager finished and shut down its four instances, then noticed two more it hadn’t started. Instead of shutting them down, it asked me. Agents only see their own part; I see all of it.

Test-first, in a complete running system

Passing tests is not the definition of done

Red first

Tests before code

Agents write tests for the intended behavior. A RED check confirms they fail before implementation begins.

Run it

Exercise the change

The agent starts the application, uses the affected feature, inspects failures and confirms it works end to end.

Stay fresh

Disposable environments

Code refreshes and rebuilds before work starts. A freshness check blocks work on a stale checkout.

The infrastructure is replaceable: laptops, VMs, containers or cloud. What matters is a runnable, testable system.

Every fleet instance gets an isolated, complete development environment with a fully working version of the system, including dependencies and test tooling. Early on I verified test-first by watching agent logs; now it’s in every development agent’s prompt, backed by the RED check. Working state lives on persistent storage separate from the compute, so a stopped agent can resume. I’ve rarely needed it, but it’s cheap insurance.

Rotating between initiatives

The limit is my attention, not agent capacity

1–3

initiatives at a time, while staying closely connected

“What are we working on? What’s next?”

How I reconnect each morning. Tickets, PRs and persisted state let the agent restore context.

Attention scales with uncertainty: routine work gets a check-in; hard work gets one-on-one pairing, sometimes for a whole day.

This is my adaptation of XP pair rotation. I work with an agent until we agree on the next objective, then switch to the next initiative while it executes. The hard part is context switching, especially the next morning. I give terminals descriptive titles to tell initiatives apart. Staying connected matters more than adding initiatives.

Tested handoffs

A PR is evidence to check, not a claim to trust

Every PR records

  • Self-review and corrections
  • What was tested in the running system
  • Results and implementation notes
  • Ticket updates and saved state

PR bundles, for multi-PR work

  1. Pin each PR’s exact revision
  2. Apply them together in one environment
  3. Rebuild and run the integrated system
  4. Run integration and health checks
  5. Reject incomplete combinations

A body of work isn’t ready for team review just because every agent reports its own task is done.

Development instances usually shut down when done, so two kinds of record survive: environment state, so a workspace can be resumed, and the engineering record in tickets and PRs. For multi-PR work I ask the manager whether everything was tested together end to end. Usually it was; when it wasn’t, the manager explains why or offers to run the bundle test, and I usually say yes.

One hard week

Writing code was no longer the bottleneck

51

PRs still waiting for review at the end of one week

If PRs wait anyway, put more into each one.

  1. AI-assisted review points out where to focus
  2. I review every PR myself
  3. Each PR shows full-system end-to-end evidence
  4. Agent-guided review for the team, who still read the changes
That week I was running a focused initiative alongside a stream of fix tickets, and still ended with 51 PRs waiting, even after merging and deploying approved ones all week. Reviewing and verifying became the bottleneck. So I changed how I build PRs to make them easier to validate. The agents’ review directs my attention; it doesn’t replace it. Review is more efficient now, and it still catches real problems.

What review is for

“Working with an AI agent is like working with an extremely talented engineer who doesn’t know the domain.”

What slips through

A business rule, an unstated expectation, a reason things are done a certain way. The code is usually good.

A recent miss

An agent added a parameter to functions that shouldn’t have it. I reviewed the shape and missed it; a teammate caught it.

What changed

Code guardrails for that case, new rules for the agents, and I now slow down and read every line.

As tech lead, I review each PR for exactly what a newcomer wouldn’t know. The widened change was reverted before release. Findings from my review go back to fleet instances, which fix them and test each PR end to end again. Only then do I post the links in the team channel. My AI developers use the same process as everyone: same PRs, reviews, approvals, merges and deployments. They respond to review comments and review colleagues’ PRs too, sometimes testing a colleague’s change in their own complete environment. None of it is hidden.

The workflow

Eight steps from request to production

Orange outline: findings loop back here

01

Describe

From existing tickets or a design discussion.

02

Implement, test

Each instance builds, then tests end to end in its own system.

03

Report

Manager reports with PR links; failures wait for me.

04

My review

Fleet review shows where to look; I read every PR.

05 · loop

Fix, retest

Findings addressed; each PR retested end to end.

06 · loop

Test together

Multi-PR work runs as a combined bundle.

07

Team review

PR links go to the team channel. Findings return to step 5.

08

Merge, deliver

Validate in dev and QA; I approve the production gate.

It’s a lot of testing. It’s also how I worked when I wrote the code myself, and that work rarely came back to me. The difference is that agents now do the repeated end-to-end retesting that’s easy for a person to cut short. After merge, my terminal agent helps coordinate deployment and uses the fleet to validate at each stage: dev, QA, then production, where we test as much as is practical and safe. The CI/CD pipeline handles progression; I keep authority over the gates.

This is a real status message from a manager. It shows evidence rather than claims, real-system testing, freshness, learning, and rotation support: it tells me when to come back. PR #[A] is on the fleet’s own repository, so this is the fleet testing an improvement to itself.

Retrospectives built the fleet

One recurring question

“What challenges did you run into during this build session, and what changes in the environment would make things easier for you?”

What improves

Provisioning, code refresh, build scripts, test automation, developer tools and the AGENT.md guidance agents read.

Who decides

I start the retrospective, choose the improvements and direct the work. Agents don’t govern their own environment.

I ask the agents, discuss their answers, decide what to improve, and direct the terminal agent or manager to make the changes. As the fleet matured, it began implementing and testing improvements to its own environment using the same instances and validation workflow it uses for application work. A fix to a shared obstacle helps every future agent. Each round starts from a better baseline.

My experience with the full set of XP practices shaped this. On one team we coordinated shared-mainline merges with a literal traffic light. The concern then is the same as now: integrate often, keep the system working, surface conflicts early. Test-first and pair rotation are established in how I work; the other practices are goals I’m still building toward, not things the tooling enforces.

In practice

Output is a side effect of small slices

6+

PRs per working day in a typical month, across more than a dozen repositories

Next day

Most PRs are reviewed and merged by the end of the next day

A few $

Per PR. A few hundred a month covers compute, inference and my terminal agent

PR volume isn’t the point. The right measure is vertical slices of value delivered; PRs are what most organizations still count.

Each epic is broken into small, verifiable slices, and each slice becomes a PR that carries end-to-end evidence and passes the same team review as everyone else’s work. Ticket counts undersell this: initiatives often arrive as one line, like “support monorepos across the entire system.” Turning that into architecture, a plan, tickets and PRs is the job. Cost: roughly half for fleet compute and inference, the rest for the terminal agent subscription. Fleet developers run on glm-5.3-flash; my terminal agent is Claude Code. The browser-based setup runs the same process for about $30 a month. The fleet costs more because every agent gets its own complete environment, not because the method needs it.

What the agents do poorly

Four weaknesses that need my attention

Stacked PRs

A merge can collapse a stack and lose the work above it. The manager now backs up first and keeps branches.

Drift

Agents drift toward what’s simplest now. One removed a Spark and Delta Lake build because Postgres handled the demo data.

Compaction

Long sessions get summarized and details vanish, even “commit and push.” I found three commits sitting unpushed.

Abstraction

Ask for ten similar things and get ten implementations. Refactoring still matters; it just has to be directed.

Agents don’t have the bigger picture unless you give it to them, any more than a junior engineer would. A teammate once reviewed my similar PRs together: “Okay, that’s three of these things. I usually refactor at three.” “So do I.” “Okay, now there are four.” “Stop the review. Let me take a look.” My agent rules now include “Check for duplication in our code.” Runs rarely fail or loop; when they do, I ask what it’s working on, or restart it. Progress lives in tickets, PRs and persisted state, so a restart costs little.

What went wrong: requirements, not code

Agents verify the software does what I specified. People who know the domain tell me whether it’s the right software.

When I misunderstand a requirement, the agents build the wrong thing well.

When I join a new organization or department, I don’t yet know its domain, and I haven’t always interpreted requirements correctly. Agent validation can’t tell me the specification was wrong. Team review caught those gaps, both in a new department and at a new company. That’s the clearest argument I have for keeping human review in the loop.

What others can adopt

Start with one agent and one working environment

01

Treat the agent as a pairing partner, and keep a human technical owner.

05

Test related changes together before merge.

02

Give it a complete, runnable system. Work test-first and exercise every change in it.

06

Keep human review, failure decisions and release approvals explicit.

03

Keep tasks small enough to validate and hand off as reviewable PRs.

07

Rotate among AI partners; recover context with terminal titles and “What’s next?”

04

Record coordination, notes and test evidence in durable work items.

08

Ask agents what slowed them down, improve the environment, repeat.

None of this requires my tools or infrastructure. I’ve run the same process on a ticket board, with sub-agents on my own machine, in browser tabs, and on separate compute instances. Getting started: give your agent everything you would do yourself, and when it can’t, ask what it needs. Have it set up the entire system and test its own work end to end. Once that works, ask it how to split the work. A low-cost subscription and an open-weight model are a good way to learn without worrying about cost; prices and models change quickly, so check what’s current.

More agents don’t automatically produce better software.

Engineering discipline, working environments, feedback loops and accountable leadership are what make parallel AI execution useful.
